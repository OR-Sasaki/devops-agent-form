# 故障観点カタログ

**このカタログは実装しない。** [D-005](./00-decisions.md#d-005-故障は今は仕込まないただし3観点の余地を設計に残す) の通り、故障の実物は後で決める。

これは **「後から弾を込められるように、器のどこに穴を空けておくか」** の一覧である。
各項目の最右列「必要な余地」が、そのまま**インフラとアプリの設計制約**になる。

用語は [CONTEXT.md](../../CONTEXT.md) に従う。

---

## 観点1: AWS 設定起因

インフラ設定の変更・誤りに由来する不具合。**担当は DevOps Agent**（インシデント調査・根本原因特定）。

この観点の狙いは、**「Terraform の変更がインシデントを引き起こしたことを Agent が突き止められるか」** を見ること。

| # | 仕込み方 | 発現する症状 | Agent に期待する回答 |
|---|---|---|---|
| 1-1 | ECS タスクロールから `dynamodb:PutItem` を剥がす | フォーム送信が全件 5xx。参照は正常 | 「タスクロールの権限変更が原因。書き込み系だけが落ちている」 |
| 1-2 | ALB のヘルスチェックパスを存在しないパスに変更 | ターゲット全台 unhealthy → 503 | 「ヘルスチェック設定の変更。アプリ自体は生きている」 |
| 1-3 | セキュリティグループの ingress を閉じる | ALB からタスクへ到達不可 | 「SG の変更で ALB→タスク間が遮断された」 |
| 1-4 | タスク定義のメモリを極端に小さくする | OOM でタスクが再起動ループ | 「メモリ割り当て不足。アプリの使用量は変わっていない」 |
| 1-5 | DynamoDB をオンデマンド → 低容量プロビジョンドへ変更 | 書き込みスロットリング、レイテンシ悪化 | 「キャパシティモードの変更がスロットリングの原因」 |
| 1-6 | サブネットのルートテーブルを壊す | ECR からイメージを pull できずタスク起動失敗 | 「ネットワーク経路の変更でイメージ取得が失敗」 |

**必要な余地（設計制約）**

- Terraform を、**健全な設定と劣化した設定を変数ひとつで切り替えられる粒度**に分解する
  例: `var.fault_injection = "none" | "iam_denied" | "bad_healthcheck" | ...`
- 上記を切り替えたとき、**必ず対応する CloudWatch アラームが鳴る**ようにアラームを設計する
- 変更が**いつ入ったか**を Agent が辿れるよう、CloudTrail が有効であること

## 観点2: アプリコード起因

アプリケーションコードのバグに由来する不具合。**担当は DevOps Agent**（RCA → 原因コミット特定 → 修正 PR）。

この観点の狙いは、**「症状からコードの該当箇所まで Agent が降りてこられるか」** を見ること。

| # | 仕込み方 | 発現する症状 | Agent に期待する回答 |
|---|---|---|---|
| 2-1 | メモリリーク（リクエスト毎にグローバル配列へ積む） | `MemoryUtilization` が漸増し、やがて OOM | 「特定コミットで導入されたリークが原因」＋該当行 |
| 2-2 | 特定入力での未処理例外（null 参照） | 条件付きで 5xx。全件ではない | 「入力 X のとき例外。バリデーション漏れ」 |
| 2-3 | 同期的な重い処理を挿入 | ターゲット応答時間の悪化 | 「レイテンシ悪化はコード変更起因。インフラは正常」 |
| 2-4 | DynamoDB への N+1 アクセス | スロットリング＋レイテンシ | 「1リクエストあたりのアクセス回数が急増」 |
| 2-5 | 毎リクエストで SDK クライアントを生成 | 徐々に劣化、接続枯渇 | 「クライアント再利用の欠如」 |

**必要な余地（設計制約）**

- **バグを一箇所に閉じ込められる構造**にする（例: フォーム送信処理を単一モジュールに集約）
- GitHub リポジトリを DevOps Agent に接続し、**デプロイイベントとコミットを相関できる**状態にする
- デプロイのたびに**識別可能なバージョン情報**（イメージタグ = コミット SHA）がメトリクス／ログに残る
- アラームが**症状ごとに分かれている**こと（メモリ・レイテンシ・エラー率を1つにまとめない）

## 観点3: セキュリティ起因

**担当は Security Agent**（脆弱性検出・ペネトレーションテスト・自動修復 PR）。
一部は運用インシデントとしても発現するため、**DevOps Agent との合わせ技**になる。

この観点の狙いは2つ。**「Security Agent が PR の時点で止められるか」**、そして
**「実際にデプロイされたものに対してペネトレーションテストで到達できるか」**。

| # | 仕込み方 | 誰が見つけるべきか | 期待する動き |
|---|---|---|---|
| 3-1 | 反射型／格納型 XSS（フォーム入力を未エスケープで表示） | Security Agent | PR コメントで指摘 → ペンテストで実証 → 修正 PR |
| 3-2 | インジェクション（DynamoDB の式インジェクション、フィルタ式への文字列連結） | Security Agent | PR コメントで指摘 |
| 3-3 | ハードコードされたシークレット | Security Agent | PR コメントで即指摘 |
| 3-4 | 認証・認可のない管理エンドポイント（`/admin` 等） | Security Agent（ペンテスト） | 到達・悪用可能であることを実証 |
| 3-5 | 過剰な CORS 設定 | Security Agent | 設計レビュー／コードレビューで指摘 |
| 3-6 | レート制限なし → 大量送信 | **両方** | Security Agent が指摘、DevOps Agent が運用影響として観測 |
| 3-7 | セキュリティヘッダ欠如（CSP 等） | Security Agent | コードレビューで指摘 |

**必要な余地（設計制約）**

- フォームが **入力を受け取り、それを表示する経路**を持つこと（= XSS の余地を作れる構造）
- Security Agent の GitHub App を**当該リポジトリのみ**に接続しておく
- ペネトレーションテスト用に、**ALB エンドポイントが外部から到達可能**であること
  → 検証は **HTTP_ROUTE**（エージェントが提示するパスにトークンを置く方式）を使うため、カスタムドメインは不要
- 3-6 のように**両エージェントにまたがる事象**を1つ持っておくと、2エージェントを併用する価値が示せる

## この3観点を成立させるための、器の要件（まとめ）

上表の「必要な余地」を統合すると、実装計画が満たすべき要件は次の通り。

1. Terraform に **故障注入用の変数**を通し、健全／劣化を切り替えられる
2. **症状ごとに分離した** CloudWatch アラームを持つ
3. CloudTrail が有効で、**設定変更の時刻と主体**が追える
4. イメージタグ = **コミット SHA** で、デプロイとコードが相関できる
5. アプリの**入力処理が単一モジュール**に集約され、バグも脆弱性もそこに仕込める
6. GitHub リポジトリが **DevOps Agent と Security Agent の両方**に接続されている
7. ALB エンドポイントが**外部到達可能**である
